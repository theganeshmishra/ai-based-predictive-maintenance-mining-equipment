# Dataset manifest

Checked October 5, 2026. "Publicly downloadable" means a public file or repository file listing was verified; it does not mean the dataset represents a mining-machine failure or has been acquired locally. Files marked "downloaded" are ignored local inputs, not GitHub uploads.

## Sensor-plus-image fault comparison: eight-category verification

**Decision: component-level benchmark architecture locked; mining-fleet validation is not complete.** The eight rows below have one GREEN and seven academically defensible YELLOW *component/fault* comparisons. They are **not eight independent mining-machine datasets or eight validated predictive-maintenance models**. G1 is reused for six categories and B1 and P1 each for one. No cross-source rows are synchronized observations, and no category label is used as a health label. Existing UCI hydraulic-leakage and PHM rock-drill-pressure results are **not** silently substituted into these pairs: their fault labels lack a verified comparable visual release.

**Week 4 status (October 5, 2026):** all eight categories and their dataset/component mappings are identified. Only **Pump** and **Belt Conveyor** have completed sensor-versus-image condition experiments. **Haul/Dump Truck, Excavator, Dozer, Wheel Loader, Drill Rig, and Grader remain planned**, with no completed matched-modality experiment or equipment-specific validation. The G1 Belt Conveyor test does not convert its five other equipment mappings into completed experiments. No Equipment #3 modelling is started in Week 4. See the [progress checkpoint](../Documentation/week_04_progress.md).

**Grade rule.** GREEN: public, real sensor and visual measurements of the same component family with the same explicit fault classes. YELLOW: the pair's condition labels match, but applying the lab component to the named mining equipment requires a stated mechanical-transfer argument. RED: absent public files or non-comparable health labels. A grade describes *dataset suitability for a condition-level experiment*, not expected model accuracy or deployment readiness.

Dataset keys (each source is a physical test rig, **not** a mine-fleet record):

- **G1 — [CORA rotating electromechanical system](https://doi.org/10.34810/DATA2500)** ([data descriptor](https://pmc.ncbi.nlm.nih.gov/articles/PMC13254333/)): a 1.43 kW motor/gearbox rig with vibration/current/temperature and **actual infrared-camera frames**. Use only the stationary `H`, `W25`, `W50`, `W75` experiments at 5, 15, 50, and 60 Hz: 4 wear states × 4 speed settings = **16 experiment runs**, one run per state/speed; the full release has 36 stationary runs and 1,878 files. Wear states are healthy and 25/50/75% imposed gear-tooth wear. Each stationary run is 45 minutes; infrared acquisition is about one frame per six seconds. The [repository's version 2.1 listing](https://dataverse.csuc.cat/dataset.xhtml?persistentId=doi%3A10.34810%2FDATA2500) shows a downloadable `W75_F15_S.mat` thermal stack (8.7 MB) and same-experiment current/temperature files; the source paper describes vibration channels too. Full original-format bundle is about 38.8 GB, but files are listed individually. Repository licence: **CC BY 4.0**. Infrared is absent from short transient runs. This is a *same-rig, same-experiment* modality pair, but frame-to-sensor-window alignment still requires checking timestamps; merely sharing a filename stem is not proof of frame-level synchronization. Six equipment rows below **reuse these same 16 runs**.
- **B1 — [University of Ottawa UODS-VAFDC](https://data.mendeley.com/datasets/y2px5tg92h/1) sensor + [XJTU-DV-Rotor](https://zenodo.org/records/17447083) event-camera:** UODS has accelerometer and microphone recordings for 20 physical bearings at three stages (healthy, developing, faulty): **60 ten-second recordings** in the full release. Use stage 0 and final stage 2, retaining only **healthy, inner-race, and outer-race** classes; stage 1 has no XJTU counterpart. UODS explicitly says its ball-fault recordings use **no load** whereas healthy/inner/outer use 400 N, so ball must be excluded to avoid making load a proxy for fault type. XJTU-Rotor has **24 event-camera recordings** in the full release, six for each of healthy/ball/inner/outer; use **18** healthy/inner/outer runs from its separate rotor-bearing rig. The event camera watches bearing-housing motion; it is not an RGB photograph of visible surface damage. Both sources are publicly downloadable under **CC BY 4.0**; XJTU's Rotor ZIP is **2.81 GB**. The XJTU [source paper](https://doi.org/10.1016/j.cjme.2025.100163) explains the visual labels. No UODS recording corresponds to a particular XJTU recording.
- **P1 — [Centrifugal Pump Multi-Fault Vibration](https://data.mendeley.com/datasets/63gjxpn7s6/1) sensor + [XJTU-DV-Pump](https://zenodo.org/records/17447083) event-camera:** the sensor release has 27 labelled XLSX files at 2 kHz. Use only files `0` (healthy), `1` (inner race), `2` (outer race), and `3` (rolling element): **four condition files**; do not mix compound impeller faults into the target. The two *publicly released* XJTU Pump ZIPs contain **72 `.dat` event recordings across six states**, at 20 and 30 Hz with six capture configurations per state/speed. Use healthy/inner/outer/ball only: **48 recordings** (12 per state). Earlier 108/72 counts, based on the paper's three-speed design, were corrected after inspecting both ZIP directories on October 4; the expected 40 Hz `.dat` recordings are **not in these public ZIPs**. Its event camera observes the pump support-bearing housing. Both datasets are public physical-rig measurements, **CC BY 4.0**. XJTU's pump archive is two ZIPs totalling **16.49 GB**. One sensor file per selected fault is *not* independent replicated failure evidence: random windows from a file cannot establish cross-machine generalization. These are comparable fault labels, not paired observations.
- **P2 — [University of Ottawa bearing vibration V2](https://data.mendeley.com/datasets/v43hmbwxpm/2) sensor proxy + P1 XJTU-DV-Pump event-camera:** real accelerometer recordings from a **bearing rig, not a pump**. The public V2 release is CC BY 4.0 and has five condition classes × four speed profiles × three trials = 60 recordings. Select only healthy (`H`), inner (`I`), outer (`O`), and ball (`B`), excluding the compound class: **48 recordings** (12 per class, six A/B training and six C/D test runs per class). Each selected MAT file holds 10 seconds of 200 kHz accelerometer and encoder data; only the accelerometer is a model predictor. All 48 selected files were individually downloaded and matched to publisher SHA-256 checks (total **631,519,512 bytes**); their file IDs and hashes are in `Results/pump_uottawa_intake.json`. This P2 proxy **adds independent recording-level evaluation**, not independent physical pumps or evidence that the same bearing specimen was absent from training. The component/fault taxonomy is a defensible analogy to the Pump support bearing under the professor's stated allowance, but empirical **pump-domain transfer remains YELLOW**.

**Architecture lock and evaluation boundary.** The canonical target is current *component condition*, not future failure time: the **six equipment mappings** using G1 collapse `H` to healthy and `W25/W50/W75` to gear-worn. G1's four wear percentages may be explored *within the source rig* but must not be interpreted as calibrated severity on a dozer, grader, or any other unlike gear. B1 uses healthy/inner/outer bearing fault type; P1 and the evaluated P2 proxy use healthy/inner/outer/ball bearing fault type. Keep three component targets, with one shared G1 experiment reused for six equipment applicability discussions. For G1, condition, speed, sensor files and infrared stack belong to the same rig experiment; do not assume each video frame has a one-to-one sensor row until time vectors are verified. For B1/P1/P2, compare **separately trained modality models at aligned fault-taxonomy level only**. Do not concatenate unrelated rows, average sensor/image accuracies as a fusion score, or claim eight-machine accuracy. Hold out physical bearing IDs or experimental conditions where feasible; the original P1 one-run-per-class sensor score remains descriptive, and P2 supplies a full-recording holdout. The capstone's `Preprocessing/cora_manifest.py` and `Preprocessing/cora_preprocessing.py` remain bounded preprocessing aids; the subsequent `Models/belt_conveyor_cora_baseline.py` evaluates one CORA component target, not six validated equipment models. No complete CORA release or mining-fleet data was downloaded.

### Final consistency check and matrix lock (October 4, 2026)

**Matrix version 1.1 is locked for the first modelling pass.** The eight-row grade decision from version 1 is unchanged: Pump is GREEN; Haul/Dump Truck, Excavator, Dozer, Wheel Loader, Drill Rig, Grader, and Belt Conveyor are YELLOW. Version 1.1 corrects the P1 public-release counts after ZIP-directory inspection: **72 released Pump event recordings across six states; 48 in the four selected states**, with 20/30 Hz data but no released 40 Hz `.dat` in those ZIPs. Every row names a condition-monitoring component, a sensor source, a visual source, compatible condition labels, access/licence, sample units, and a transfer caveat. The P1 visual model has since been evaluated; GREEN remains a **source/label-compatibility grade**, not a claim of completed fair sensor-versus-image validation.

**Change control:** if a file inspection later contradicts a source label, channel description, licence, or run grouping, revise this matrix and grade before using the affected pair in a reported model. Do not silently substitute UCI hydraulic, PHM drill pressure, ESPset, or belt-crack labels for the frozen targets.

**Pump intake and experiment after lock.** The four selected P1 XLSX files were downloaded individually into ignored `Raw_Data/pump_bearing/` and verified by SHA-256. With `header=None` they contain one vibration column and, in class order healthy/inner/outer/ball, **61,440 / 57,344 / 57,344 / 61,440 samples** at the source-stated 2 kHz. The first numeric row is data, not a header. The initial model in `Models/pump_bearing_baseline.py` uses 1,024-sample non-overlapping windows and a chronological train/gap/test split *within each of these same four files*. Its `Results/pump_bearing_exploratory.json` score is a pipeline diagnostic only: one run per class makes independent-run accuracy **unavailable**. `Models/pump_event_visual_baseline.py` uses selective HTTP-range reads of the released ZIP members, with **all 48 selected runs processed** for their first two seconds and eight 250 ms event images per run. ## Active, inspected datasets

### UCI Condition monitoring of hydraulic systems

- **Equipment:** shared hydraulic subsystem analogue for excavator, dozer, wheel loader, and grader; not measurements from those machines.
- **Source / citation:** Helwig, Pignanelli, and Schütze, [UCI dataset](https://archive.ics.uci.edu/dataset/447), DOI [10.24432/C5CW21](https://doi.org/10.24432/C5CW21).
- **Licence / access:** CC BY 4.0; public ZIP downloaded and SHA-256 checked.
- **Provenance / size:** real measurements from a controlled experimental hydraulic rig; 2,205 operating cycles, 17 channels; 73 MB ZIP, 556 MB uncompressed text.
- **Modalities / labels:** pressure, flow, temperature, vibration, motor power and virtual efficiency; cooler, valve, pump-leakage, accumulator and stability labels. Pump leakage has three classes: no, weak, severe.
- **Planned and completed task:** current pump-leakage severity classification. 1,449 stable cycles retained. Four cycle-level summary features per channel; no missing/non-finite feature values. 68 features total. Train/validation/test split holds out full four-component condition combinations.
- **Pairing:** sensor channels and labels are paired by cycle **within UCI**. No equipment photographs. No relation to any CV dataset.
- **Limits:** no mining vehicle IDs, dated repairs, future failure horizon or RUL. Reusing it for four categories does not create four independent mining datasets.
- **Files / output:** ignored `Raw_Data/uci_hydraulic/`, ignored `Processed_Data/`; small local `Results/uci_hydraulic_pump_leakage.json` and `Figures/uci_hydraulic_pump_leakage.png` are not yet committed.

### ESPset V3

- **Equipment:** electric submersible centrifugal pumps used in offshore oil production; possible pump-subsystem analogue, **not mining data**.
- **Source / citation:** Pellegrini et al., [ESPset V3](https://data.mendeley.com/datasets/m268jsw339/3), DOI [10.17632/m268jsw339.3](https://doi.org/10.17632/m268jsw339.3); [publisher code](https://github.com/NINFA-UFES/ESPset).
- **Licence / access:** CC BY 4.0; public `features.zip` downloaded and SHA-256 checked. `spectrum.zip` not acquired.
- **Provenance / size:** real offshore tests; 6,032 rows from 11 pump IDs; `features.zip` 258 KB, seven numeric extracted predictors plus `id`, `esp_id`, and `label`.
- **Modalities / labels:** vibration-spectrum-derived features; Normal 4,801, Unbalance 576, Faulty sensor 295, Rubbing 290, Misalignment 70. No missing values. Sixty-eight identical feature rows exist, but no identical vector crossed the selected train/validation/test splits.
- **Planned and completed task:** binary current abnormal-versus-normal classification. The first baseline holds out complete pump IDs: six train, two validation, three test. `id` and `esp_id` are excluded from model predictors. A five-class model is deferred because misalignment occurs on only two pumps and cannot be represented independently in three pump-held-out splits.
- **Pairing:** features and labels are paired within ESPset. No images; not paired with XJTU-DV-Pump or any other visual dataset.
- **Limits:** 11 source pumps, no dated repairs/RUL, offshore-to-mining transfer not validated.
- **Files / output:** ignored `Raw_Data/espset_v3/`, ignored `Processed_Data/`; small local `Results/espset_v3_binary_fault.json` and `Figures/espset_v3_binary_fault.png` are not yet committed.

### PHM 2022 hydraulic rock drill (rockdrill11)

- **Equipment:** a rock drill used on mining drill rigs; source cycles were recorded in a controlled Epiroc test cell, not underground during production.
- **Source / citation:** Jakobsson, Frisk, Krysander, and Pettersson (2022), [official PHM Society data challenge](https://data.phmsociety.org/2022-phm-conference-data-challenge/), [dataset paper](https://doi.org/10.36001/phmconf.2022.v14i1.3144).
- **Licence / access:** official public training ZIP downloaded and SHA-256 checked (`0a49a31af500e40a00d4949020e41c6b41422ae3fc4895aeb0675c0002427719`). The paper is CC BY 3.0, but the download page does not clearly specify a separate licence for the CSV files; keep raw files local and do not redistribute them.
- **Provenance / size:** controlled fault induction on a mining-relevant rock drill. The labelled training archive is 235 MB compressed / 661 MB of CSV, with 34,045 impact cycles from five source configurations (1, 2, 4, 5, 6). Three aligned pressure-signal files per configuration: `pin`, `pdmp`, and `po`. Signals contain 571–748 samples per cycle across the inspected files; source paper reports 50 kHz acquisition and per-cycle normalization.
- **Modalities / labels:** pressure signals only; label 1 no fault and labels 2–11 ten fault/condition types (including seal leakage, accumulator damage, valve damage, and flow/orifice changes). No missing or non-finite values found in the processed cycles. Each of the 11 labels occurs in every configuration; precise counts are in the result JSON.
- **Completed task:** 11-class current-condition diagnosis. Per sensor: 32 interpolated shape values plus nine statistical/spectral features, giving 123 features. Configurations 1/2/4 train, 5 validation, 6 test; feature selection uses training data only. The selected 32-feature forest achieved 0.794 accuracy and 0.776 macro F1 on the 3,293-cycle held-out test configuration. Labels 5 and 10 have low recall (0.294 and 0.160), so this is not uniformly reliable across faults. This is a local split of the labelled training set, **not** the challenge's official blind score.
- **Pairing:** the three pressure channels match by row/cycle within a source configuration. No paired drill photographs or repair records; DsDPM-66 images cannot be joined at sample level.
- **Limits:** five labelled training configurations and controlled test-cell faults; no field generalization test, dated repairs, future failure horizon, or RUL. Neighbouring cycles are correlated, which is why configurations rather than individual cycles are held out.
- **Files / output:** ignored `Raw_Data/phm2022_rock_drill/` and `Processed_Data/`; local `Results/phm2022_rock_drill.json` and `Figures/phm2022_rock_drill.png`.

## Comparison policy

1. A source with only equipment-category annotations may support image *identification*, not condition monitoring.
2. Independently collected sensor and visual data may be compared at equipment/component/fault-category level only if their labels and evaluation units genuinely match. They are never joined row by row.
3. A numerical comparison across separate datasets is descriptive, not a test that one modality is better. Dataset shift, prevalence, and source-machine differences must be stated.
4. G1 CORA contains both physical sensor signals and infrared frames from the same stationary experiment. The Belt Conveyor analysis now has **whole-speed, run-level held-out folds**, but a *sample-level* fusion score would still require verifying per-modality time vectors, synchronization, and a valid design for the tiny number of runs. B1 and P1 do not permit sample-level fusion because their modalities come from different rigs. No reported result is a valid sensor-plus-image fusion score.
5. Current tests identify existing conditions. Predictive maintenance in the strict sense requires future failure or repair outcomes; do not call a contemporaneous fault classifier a validated RUL predictor.
