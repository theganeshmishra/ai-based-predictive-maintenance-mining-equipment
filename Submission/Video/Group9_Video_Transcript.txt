01:15  The problem and objectives
Mining operations depend on components such as bearings, motors and geared drives. A fault in one component may interrupt the larger process. The project asks whether available condition-monitoring measurements can support a practical fault-classification prototype. The software objective is straightforward: accept a supported file, apply the correct preprocessing, load an existing model, and display its predicted condition. The research objective is harder: compare sensor and visual evidence using fault targets that are mechanically comparable, and test how results change under proper group separation. A working upload button alone cannot establish that a classifier generalizes. For that reason, the project keeps software execution checks separate from held-out experimental performance. Both are necessary, but they answer different questions.

02:12  Research background
The research background combines conventional condition monitoring with visual transfer learning. Sensor measurements can be summarized using statistical and spectral features, making tree ensembles, support vector machines and logistic regression useful candidates. Random forests provide a practical baseline for mixed numerical features. For visual inputs, the project uses ImageNet-pretrained ResNet18 representations. Most visual routes fine tune a classifier, while the gear-tooth photograph route uses frozen features with logistic regression. These algorithm choices do not remove weaknesses in the data. A model may learn a recording, operating speed or camera setup instead of a transferable fault signature. The central methodological choice is therefore the way training and testing are separated. Dataset sources and model references are listed in the references chapter near the end of this video, and in the final report.

03:15  Eight application mappings
The system contains eight mining-equipment application mappings: Pump, Haul Truck, Belt Conveyor, Dozer, Excavator, Wheel Loader, Drill Rig and Motor Grader. These names describe intended applications of laboratory components. They do not mean that every dataset was collected from the named mining machine. Pump and Haul Truck use bearing-related evidence. Conveyor and Dozer use geared-drive evidence, with Dozer reusing the conveyor benchmark. Excavator and Wheel Loader use related drive and motor tasks. Drill Rig uses gearbox data, while the aligned Motor Grader comparison concerns gear damage. The original Motor Grader bearing route is also preserved as a separate task. Reuse of the same rig or records is explicitly disclosed, so eight application rows are not presented as eight independent field trials.

04:12  Dataset provenance
The sensor sources include Ottawa and UODS bearing measurements, CORA electromechanical measurements, MCC5 gearbox vibration, Aalto gear measurements and the separate JUST bearing task. Visual sources include XJTU dynamic-vision recordings, CORA infrared frames, synthetic MFGNet gear renders and real GearBox tooth photographs. Event-camera frames are not ordinary colour photographs. Synthetic renders are not camera measurements from damaged mining equipment. Multiple frames, windows or tooth crops may come from one source group, so their count must not be confused with a count of independent machines. The dataset manifest records the source mappings and available local files. Raw data and large checkpoints stay outside the public code archive, and the local installation needs access to those prerequisites.

05:09  System block diagram
The block diagram begins with a file supplied through the notebook, command line or local upload page. The system validates the input and tries to identify a known source format. If the source is compatible with more than one equipment mapping, it returns an ambiguity warning rather than silently guessing. A sensor file is converted into the features expected by its checkpoint. An image is transformed according to the visual route. The saved model produces class probabilities, and the largest output determines the displayed condition. Both modalities share the same prediction entry point, but they remain independent models. There is no fusion of unrelated sensor and image samples. The final output includes the application mapping, fault label, model probability and model used.

07:45  Load sensor data
The sensor loading code examines known file structures rather than accepting every numerical table as interchangeable. Supported CSV schemas identify expected channel names for Ottawa, UODS, MCC5, JUST and Aalto sources. Original MAT recordings are also supported for relevant bearing sources. CORA recordings have a source-specific naming and acquisition convention. These checks matter because sampling rates, channel meanings and units affect the extracted features. A pressure column cannot be substituted for an acceleration channel merely because both contain numbers. The application rejects an unrecognized CSV schema instead of passing incompatible values into a model. Source recognition is not a universal machine-identification algorithm; it identifies compatibility with the laboratory pipelines already implemented in this project.

08:44  Cleaning and feature preparation
Cleaning in this project means validating the measurements and applying the source-specific preparation expected by a model. Readers check numeric values and whether enough samples are available for a complete feature window. Later checks reject nonfinite features and feature sets that do not match the checkpoint. These controls prevent a model from receiving the wrong columns in the wrong order. Sensor features include quantities such as root mean square, standard deviation, crest factor and selected frequency-domain summaries. Some sources use shaft-order information when rotational speed is available. Preprocessing is not simply deleting missing rows and hoping for a good score. Its purpose is to preserve a consistent relationship between the original measurement, the extracted features and the model that was trained on them.

09:36  Why the feature definitions matter
Root mean square is the square root of the average squared signal amplitude. It summarizes signal energy but does not independently identify a particular fault. Crest factor compares a peak amplitude with the root mean square value and can describe impulsive behaviour. Spectral features summarize the distribution of energy across frequency. In sources where speed is known, shaft-order features express frequency relative to rotation. These measurements can change with operating conditions as well as damage, which explains why speed and load separation are important. The model learns combinations of features from labelled examples. A large feature value is not automatically a failure warning. At inference, the selected checkpoint determines exactly which feature columns are required and which preprocessing pipeline must be applied.

10:31  Keep complete groups apart
The main evaluation safeguards are visible in the notebook split demonstration. Complete recordings or operating groups are assigned to the test side. Individual windows from a held-out recording cannot be placed in training. Pump uses separate speed profiles or operating speeds for its two datasets. CORA holds out whole speed settings. Haul Truck sensor evaluation uses held-out bearing identities. The aligned Motor Grader sensor experiment leaves gear pairs out, while its photo task uses source groups. These protocols are not identical, and their differences remain part of the interpretation. Inner validation selects models or training settings within the training data. This reduces direct leakage from the final evaluation group, although dataset confounding and limited independent specimens can still restrict scientific conclusions.

11:29  Sensor model selection
The sensor code defines several candidate classifiers rather than forcing a single algorithm onto every dataset. The candidate family includes random forest, extra trees, histogram gradient boosting, a radial-basis support vector machine and logistic regression. Scaling is contained inside the relevant estimator pipeline, so its parameters are fitted with training data. Class weighting is used where configured. The chosen candidate can differ across evaluation folds and across application mappings. The notebook displays these settings by instantiating the candidate factories and reading their parameters. Deployment uses the saved final estimator and its selected feature list. It does not repeat candidate selection each time a user uploads a file. This keeps inference reproducible and avoids confusing prediction latency with a new training experiment.

12:27  Image model inference
The visual route reads a supported image, applies its configured transforms and uses a saved model to obtain probabilities. Seven main image routes use ResNet18-based classifiers. Motor Grader tooth photographs follow a separate path: frozen ResNet18 features feed a logistic-regression classifier. This distinction is important when explaining which model produced an answer. Inference runs without gradient calculation and with the model in evaluation mode. The system is not trained to diagnose arbitrary whole-machine photographs. Supported event frames, thermal frames, synthetic gear renders and tooth crops have different visual meanings and provenance. A photo of an entire grader does not provide the same evidence as a labelled tooth inspection crop. Unknown image sources must remain unsupported or ambiguous.

13:23  Data augmentation and selected models
Data augmentation is applied only to training images, never to validation or test images. It imitates nuisance variation that should not change the fault label, and a seeded random generator keeps runs repeatable. Event-camera and infrared frames receive random horizontal flips, shifts of up to eight pixels, brightness scaling between zero point eight and one point two, and small Gaussian noise. Rendered gears are rotated by multiples of ninety degrees, mirrored and shifted by up to six pixels, because a gear looks the same when it is turned or reflected. The gear-tooth photo route uses frozen features and is not augmented. Sensor recordings are not augmented either; each recording already gives many windows, and class weighting handles imbalance. Across the thirty-five outer evaluation rounds, inner validation selected logistic regression thirteen times and extra trees twelve times. Gradient boosting was chosen five times, random forest three times and the RBF support vector machine twice. No single classifier won every mapping, which is why the full candidate set is kept.

14:36  The central prediction function
The central prediction function is the connection between the notebook, command line and local upload page. It first handles the special tooth-image route when Motor Grader is explicitly selected. Other inputs are passed through source identification. If a user selects a mapping incompatible with that source, the function raises an error. If the source matches several candidates and no reliable choice has been made, it returns an ambiguous equipment result. Otherwise it scores the appropriate checkpoint, selects the most probable class and assembles the answer fields. The common entry point reduces the risk that different interfaces accidentally apply different preprocessing. It also keeps source identification separate from fault classification, which is essential for equipment mappings that share one laboratory dataset.

15:30  Notebook upload interface
The notebook upload interface uses a file-upload widget, a mapping dropdown and a prediction button. The upload accepts supported sensor recordings or image formats, but format acceptance does not guarantee source compatibility. The callback first checks whether a file was actually supplied. It then passes the temporary input to the same application prediction function. Automatic routing is useful only where the source can be established. The dropdown remains necessary for shared laboratory formats and the explicit gear-tooth inspection route. The interface should display either a condition prediction with its model information or a clear explanation of why the input cannot be scored. A user confirmation selects an application mapping; it does not turn laboratory data into real measurements from that mining machine.

19:46  Ambiguous equipment is a valid result
This execution supplies a compatible CORA recording without selecting an equipment mapping. The expected behaviour is an ambiguous equipment response listing the supported candidates. The system cannot infer that an identical laboratory source must belong to one particular whole mining machine. This is a reliability feature, not a missing classification trick that should be bypassed with a guess. Manual mapping confirmation allows a known task to be evaluated, but it does not create new evidence about the original physical machine. The same principle applies to image provenance. A visually similar frame can remain ambiguous when its source index cannot establish a unique route. The final demonstration should explain this behaviour clearly rather than presenting every upload as automatic identification.

20:38  Invalid inputs and errors
The invalid-input examples test ordinary text, an unrecognized CSV and corrupted image bytes. These checks matter because an upload control can accept a filename even when the content is unusable. The model-loading path also verifies checkpoint trust and expected metadata. A missing or untrusted checkpoint must not be replaced with a random estimator or a fabricated prediction. Errors should explain why the input could not be scored, while leaving the working application stable. These examples demonstrate handling of specific tested cases; they are not a guarantee that every imaginable malformed file has been exhausted.

22:19  Independent experimental results
The final report contains the independent experimental results. Pump reached ninety-five point eight three percent sensor balanced accuracy and one hundred percent visual balanced accuracy under their respective recording protocols. Those protocols and rigs differ, so the result does not establish that vision is universally better. The CORA tasks showed weak transfer to unseen speeds. Haul Truck had weaker visual recognition and a load-confounded ball-fault class. Motor Grader's aligned gear sensor result was seventy-seven point seven eight percent balanced accuracy, while the tooth-photo result was eighty-two point five nine percent. Its high raw photo accuracy is affected by class imbalance, and damaged-tooth recall is lower. The poster shows these same held-out balanced accuracies, and the report gives the full numerical evidence.

23:15  Time split versus held-out groups
Supplementary time-split checks use the first sixty percent of a recording for training, discard a ten percent gap and test on the last thirty percent. Several saved results are much higher than the unseen-speed results. This is not a reason to hide the more difficult evaluations. The two protocols ask different questions. A later segment of a known recording can retain the same speed, specimen and acquisition signature as training. A gap reduces direct temporal overlap, but it does not create a new machine or operating condition. The report labels these scores separately and notes that fitting settings and sample pools can differ. No score from this procedure establishes future failure forecasting, and no unsupported time-split result is assigned to a mapping without a saved experiment.

24:07  Applications and remaining limits
The practical outcome is a working educational prototype for component inspection and reproducible model comparison. It demonstrates data ingestion, feature preparation, trusted model reuse, ambiguity handling and prediction output through a common interface. Its remaining limitations are scientific as well as operational. Some datasets share records, image crops remain related, synthetic renders need validation against real photographs, and confidence values are not calibrated failure risks. The code package also needs local data and checkpoints to run the full demonstration. Before a real maintenance decision could rely on this system, additional work would need site-specific measurements, balanced operating conditions, independent machines and a clear assessment of missed-fault costs. The present software should support investigation and explanation, not replace qualified engineering judgment.

26:07  Final demonstration summary
To conclude, the coding phase provides one integrated notebook backed by a reusable Python implementation. It accepts supported sensor recordings or component images, checks source compatibility, loads an existing model and returns a fault label with model information and probability. Where source evidence cannot distinguish equipment mappings, the system reports ambiguity rather than guessing. Real local execution checks confirm that the supported routes run, including the aligned Aalto gear sensor and Motor Grader tooth-image paths. The final report explains the actual held-out results, the supplementary time-split check and the unsuccessful cases. The project is complete as a laboratory-based demonstration with scientific limitations. Future work should improve independent data and validation before expanding claims about mining-field reliability or future failure prediction. Thank you for watching.
